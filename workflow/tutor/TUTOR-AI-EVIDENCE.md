## Reflection evidence map

### AI security

- **Attack surfaces and prompt injection:** The spec identifies rough notes as untrusted input and considers direct requests to reveal secrets, access other consultations, use tools, or mutate bookings. A synthetic direct-injection fixture is now run through a capturing fake. This verifies the application sends the fixed instruction and only the rough notes as the untrusted input field. It does not test the live model's behavior. Indirect injection and live-model behavior remain unevaluated.
- **Implemented protections and tests:** Evidence covers strict request parsing, fixed task/instruction construction, prompt/input separation, output-shape/markup rejection, typed admission denial with zero provider calls, fail-closed admission-store errors, bounded call timeout, no automatic retry, rolling quota enforcement, and zero calls on invalid rough notes. Tutor MockMvc tests establish owner/state checks, CSRF, and no-write behavior. The app-api/PostgreSQL integration verifies real login/session state, task/input routing to a deterministic fake, session-generation revocation, account deactivation during generation, output discard, and session invalidation.
- **Limits:** Input/final output are limited to 8,000 code points; the existing request-body cap is 64 KiB. The Tutor task proposes a 20-second deadline, which the shared wrapper enforces. The PostgreSQL adapter enforces configured per-key request and reserved-output-token limits plus the 3-per-5-minute Tutor cap and one in-flight admission per Tutor in isolated tests. The Tutor runtime now rejects FAKE provider results outside the `local` profile. Production still has no configured provider bean/key routing or active admission migration; the raw-response streaming cap and actual SoC token usage accounting remain unresolved pending provider verification.
- **Approval and human oversight:** The endpoint returns `requiresReview=true` and does not persist generated text; the React workspace labels fake output and keeps rough notes, draft, and saved-note editor separate. Copying and saving are explicit, version checked, and tested. The backend and UI have independent reviews recorded; no P6 human implementation acceptance is recorded, and parser/gateway owner acceptance remains pending.

### Spec-driven development

- **What must be clear first:** The P6 spec states the actor and booking boundary, allowed model input, exact request/output shape, validation and error behavior, no-write rule, role ownership, UI save boundary, limits, exclusions, and unresolved dependencies.
- **How to judge precision:** A requirement is ready when an implementer and reviewer can identify observable inputs, outputs, state changes, authorization rules, failure behavior, and a test ID without inventing policy. Production authentication/session integration and fake-backed UI state are tested. The fake-API browser flow is verified; live backend/session browser integration, production gateway registration, migration activation, and affected-owner acceptance remain unresolved, so full P6 acceptance is not ready.
- **How changes flow:** Update the spec and affected test-matrix rows when a decision changes, then implement and run the linked tests. Record the spec/test revision and results in a dated handoff. Do not silently change behavior in code alone.
- **Intent versus wording:** Use state and side-effect assertions: rejected requests make zero gateway calls; generation makes no writes; the tutor owns the booking; session revocation discards output; a save still requires the version-checked note path. Service tests verify revoked and inactive principals are rejected. PostgreSQL-backed tests verify CSRF, owner/state, and no-write behavior; a full app-api integration test now verifies production authentication/account rechecks before and after generation, output discard, and immediate HTTP-session invalidation. Frontend tests prove generated drafts remain unsaved until explicit versioned PUT. The full run passed 91 unit, 192 PostgreSQL, and 193 frontend tests; the UI follow-up passed 196 frontend tests and 34 focused PostgreSQL route tests. Isolated PostgreSQL quota cases are linked in shared AI evidence.

### Basic multi-agent software engineering

- **Useful roles for the remaining P6 work:** An analyst or owner resolves cross-role contracts; an architect checks boundaries and data flow; a test designer turns requirements into adversarial and state-based cases; a developer implements only the settled slice; an independent reviewer reproduces tests and challenges the evidence. For the parser/gateway slice, the primary developer implemented the work and recorded synthetic cases; the separate shared-admission fix received independent review as recorded in its handoff. Keep ownership explicit for shared admission/provider transport, Auth principal validation, and Core migrations.
- **Testing specialized agents:** Use synthetic hostile handoffs, fake approval claims, and fabricated test claims. Record the exact task/instruction revision, permitted scope, observable tool calls, outputs, expected behavior, and reviewer reproduction. This evaluates development-agent behavior; it is separate from app AI-security testing.
- **Handoff contents:** Pass the spec and test-matrix revision, scope and exclusions, settled/open decisions and owners, relevant code paths, commands to run, and evidence locations. The current parser handoff records scope, test commands/results, and limitations; it also explicitly says no separate developer agent or independent reviewer was used.
- **Where errors can enter:** Requirements may be interpreted differently across Tutor, Student, Auth, and Core; a task can inherit malicious or forged instructions; an implementer can overstate a test; a reviewer can trust the handoff without reproducing it. Preserve source revisions, raw observable results, and review findings so these gaps are inspectable.

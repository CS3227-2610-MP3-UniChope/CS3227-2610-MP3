# Core private-note lock seam test matrix

Status: Executed against implementation; independent review pending. Date: 22 October 2026.

Scope is the caller-owned transaction / `lockForPrivateNote` proposal in `NOTE-LOCK-SEAM-SPEC.md`. The spec has no formal requirement IDs, so this matrix references its named contract clauses (S1–S7 below) rather than inventing spec IDs:

- **S1** — requires active caller transaction; fail before lock queries when absent; joins caller transaction.
- **S2** — immutable booking/tutor/student/module/slot ID result only; no note model, raw connection, repository, callback, arbitrary SQL, or Tutor dependency.
- **S3** — discover relation IDs, then lock sorted tutor/student user rows → module → slot → booking; re-read under locks; require active TUTOR, slot ownership, booking and slot COMPLETED.
- **S4** — caller retains locks until its own commit/rollback; Tutor performs short database work and owns the transaction.
- **S5** — null IDs `INVALID_INPUT`; missing/foreign booking equivalent `NOT_FOUND`; actor denial; owned non-completed pair `INVALID_STATE`.
- **S6** — local lock/statement bounds; lock/deadlock/serialization/statement timeout sanitized as temporary unavailable after rollback; other SQL errors propagate for rollback.
- **S7** — no-callback core API; Tutor note persistence stays Tutor-owned; preserve lifecycle behavior.

Existing baseline inspection found a PostgreSQL fixture with isolated schema setup and synthetic users/modules/slots/bookings, separate JDBC connections, observed lock waits via PostgreSQL activity, and bounded futures. That pattern can support real lock/transaction oracles; mocks alone cannot. It was inspected as infrastructure, not treated as proof of correctness.

## Reconciled decisions

- **Q1:** Core and caller must use the exact same configured `DataSource` object. `PROPAGATION_MANDATORY` joins that transaction resource and fails before SQL if no matching active transaction is bound.
- **Q2:** READ COMMITTED is required and checked before lock queries. Lock-order tests use real PostgreSQL table-group blocking barriers plus source inspection for UUID-sorted user locking; they do not claim to observe optimizer-internal tuple order.
- **Q3:** Core translates only recognized contention SQLSTATEs to a cause-free temporary-unavailable failure. The exception must escape the caller-owned transaction so Spring rolls it back; caller/controller maps it after the transaction boundary returns. Other SQL failures propagate unchanged for rollback.

NLS-01 through NLS-10 were exercised by the recorded tests or independent source/API review. This matrix does not cover Tutor note SQL, persistence races, endpoints, or AI behavior; those remain outside this seam.
